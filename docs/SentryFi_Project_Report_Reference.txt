1.1 Background: AI in Financial Security
-----------------------------------------
The global financial system faces escalating threats from cybercriminals,
fraudulent invoicing, phishing attacks, and regulatory non-compliance.
According to cybersecurity reports, phishing attacks account for over 36% of
all data breaches, and invoice fraud alone costs global enterprises billions
of dollars annually. Anti-Money Laundering (AML) violations and SOX
(Sarbanes-Oxley Act) compliance failures further expose organizations to
regulatory sanctions and reputational damage.

Traditional rule-based detection systems are insufficient against the
increasingly sophisticated and adaptive nature of financial threats. Machine
Learning offers a paradigm shift by enabling pattern recognition at scale,
anomaly detection in structured data, and natural language understanding of
regulatory documents -- all without the need for exhaustive manual rule sets.

1.2 Core Problem Areas Addressed
----------------------------------
SentryFi addresses three distinct and critical financial security domains:

  (a) PHISHING URL DETECTION
      Financial phishing attacks direct victims to spoofed websites mimicking
      banks, payment platforms (PayPal, Chase, Wells Fargo), and crypto
      exchanges. Attackers use suspicious TLDs (.xyz, .top, .ru, .tk),
      obfuscated domains, and embedded financial keywords to build deceptive
      URLs. A trained classifier can structurally analyze URLs before a user
      visits them.

  (b) INVOICE FRAUD / ANOMALY DETECTION
      Invoice tampering involves manipulating line-item totals, applying
      unauthorized tax rates, or creating fictitious invoices. Statistical
      anomaly detection using Isolation Forest can identify invoices whose
      numerical patterns deviate significantly from the normal financial
      distribution of legitimate documents.

  (c) REGULATORY COMPLIANCE VIOLATIONS
      Financial documents including contracts, payment memos, and audit
      reports often contain clauses that violate AML guidelines, SOX controls,
      or standard payment terms. NLP-based text classification can
      automatically flag these violations at a clause level for human review.

1.3 Objectives of SentryFi
----------------------------
  1. Build and train three domain-specific ML models for financial threat
     detection.
  2. Expose the models through a REST API using FastAPI with OCR document
     processing.
  3. Create a professional, production-grade React dashboard enabling
     real-time scanning and audit trail management.
  4. Integrate Firebase Authentication and Firestore for secure user
     management and persistent scan history.
  5. Deploy the system with graceful fallback mechanisms to ensure reliability
     even when cloud services are unavailable.

  - A response interceptor automatically retries requests on HTTP 502/503/504,
    accommodating ML model cold starts with a 2-second delay before retry.

    (file uploads) or JSON (URL scans).
  - After receiving ML results, the frontend writes a scan record to Firestore
    via firestoreService.js, with a localStorage fallback if Firestore fails.

4.1 Phishing URL Classifier
-----------------------------
File    : backend/ml/train_phishing.py
Model   : Random Forest Classifier (inside sklearn Pipeline)
Artifact: backend/models/phishing_model.joblib (105 KB)

FEATURE ENGINEERING - URLFeatureExtractor:
  A custom scikit-learn transformer (BaseEstimator, TransformerMixin) converts
  each raw URL string into an 8-dimensional numerical feature vector.

  Feature 1 - url_length:
    Total character count of the URL string. Phishing URLs are typically longer
    to obscure the true domain with subdomains and path segments.

  Feature 2 - dot_count:
    Number of '.' characters. Multiple subdomains are a classic indicator:
    e.g., secure.paypal.login.xyz.top has 4 dots.

  Feature 3 - hyphen_count:
    Number of '-' characters. Legitimate domain names rarely use multiple
    hyphens, while phishing domains use them to mimic real brands.

  Feature 4 - at_count:
    Presence of '@' in the URL. Browsers treat text before '@' as credentials
    and navigate to the host after '@', making 'user@malicious.com' dangerous.

  Feature 5 - has_ip:
    Binary flag. Regex pattern \b(?:\d{1,3}\.){3}\d{1,3}\b detects raw IPv4
    addresses used instead of domain names (e.g., http://54.123.43.122/login).

  Feature 6 - has_suspicious_tld:
    Binary flag. tldextract library parses the TLD accurately. Checks against
    curated high-risk TLD list: [xyz, top, ru, tk, cc, info, biz].

  Feature 7 - entropy (Shannon Entropy):
    Measures information randomness of the URL. Formula:
      H(X) = -sum(p(x) * log2(p(x))) for all unique characters x.
    High entropy indicates randomly generated or encoded subdomains.

  Feature 8 - keyword_count:
    Count of financial/authentication keywords in the URL from the list:
    [login, secure, bank, verify, kyc, wallet, paypal, crypto].

ALGORITHM - RandomForestClassifier:
  - 100 decision trees (n_estimators=100)
  - Maximum tree depth of 10 to prevent overfitting
  - Binary output: 0 = Legitimate, 1 = Phishing
  - predict_proba() provides per-class probability scores

TRAINING DATA:
  - Primary: Attempts real phishing dataset download from GitHub
  - Fallback: 10,000 synthetic URLs (5,000 legitimate + 5,000 phishing)
    * Legitimate: Randomly prefixed well-known domains (google, chase, paypal,
      amazon, netflix, github, bankofamerica, citi, linkedin, twitter)
    * Phishing: Templates with suspicious TLDs (.xyz, .top, .ru, .tk, .cc)
      and embedded keywords (paypal-security-update, kyc-update, wallet-verify)

TRAINING PIPELINE:
  Pipeline([
    ('features', URLFeatureExtractor()),
    ('classifier', RandomForestClassifier(n_estimators=100, random_state=42,
                                           max_depth=10))
  ])
  80/20 train/test split, random_state=42

INFERENCE FLOW (/api/v1/scan/phishing):
  Input  -> { "url": "http://paypal-secure.xyz/login" }
  Step 1 -> URLFeatureExtractor transforms URL to 8-feature vector
  Step 2 -> RandomForest predicts class and probabilities
  Step 3 -> risk_score = confidence*100 (phishing) or (1-conf)*100 (clean)
  Step 4 -> Heuristic flaggedReasons generated from URL content
  Output -> { riskScore, verdict, confidence, flaggedReasons, scannedAt }

4.2 Invoice Anomaly Detector
------------------------------
File    : backend/ml/train_invoice.py + backend/services/ocr_service.py
Model   : IsolationForest (unsupervised anomaly detection)
Artifact: backend/models/invoice_model.joblib (854 KB)

OCR PIPELINE (ocr_service.py - process_invoice_file):
  Accepts raw file bytes and filename; returns feature dict.

  PDF  -> pdfplumber.open(BytesIO(bytes)) iterates pages -> extract_text()
  JPG/PNG -> pytesseract.image_to_string(Image.open(BytesIO(bytes)))
  TXT  -> file_bytes.decode('utf-8', errors='ignore')
  Fallback -> default text "Subtotal: $1000.00 Tax: $100.00 Total: $1100.00"

REGEX FEATURE EXTRACTION (parse_invoice_text):
  Pattern for subtotal: r'(?:subtotal|sub-total)[\s:]+\$?([\d,]+\.\d{2})'
  Pattern for tax     : r'(?:tax|vat)[\s:]+\$?([\d,]+\.\d{2})'
  Pattern for total   : r'(?:total|amount due)[\s:]+\$?([\d,]+\.\d{2})'

  Feature 1 - tax_to_subtotal_ratio = tax_amount / subtotal
    Normal invoices: approximately 0.08 to 0.12 (8-12% tax rate)
    Anomalous: below 0.02 or above 0.20

  Feature 2 - line_item_sum_delta = |total - (subtotal + tax_amount)|
    Normal: near 0 (rounding errors < $1)
    Anomalous: significant discrepancy ($10 to $5,000)

  Feature 3 - round_amount_score = 1 if subtotal % 100 == 0 else 0
    Fraudsters commonly use exact round amounts to fabricate invoices.

  Feature 4 - amount_z_score = (subtotal - 500) / 300
    Proxy for how unusual the subtotal amount is relative to baseline.
    Extreme values (>3 or <-2) indicate potential fraud.

TRAINING DATA GENERATION:
  Normal samples (95% - 9,500 rows):
    tax_to_subtotal_ratio ~ Normal(mean=0.10, std=0.02)
    line_item_sum_delta   ~ Exponential(scale=1.0)
    round_amount_score    ~ Binomial(n=1, p=0.05)
    amount_z_score        ~ Normal(mean=0, std=1)

  Anomalous samples (5% - 500 rows):
    tax_to_subtotal_ratio ~ Uniform(0.0, 0.4)
    line_item_sum_delta   ~ Uniform(10, 5000)
    round_amount_score    ~ Binomial(n=1, p=0.7)
    amount_z_score        ~ Uniform(3, 15)

ALGORITHM - IsolationForest:
  - Unsupervised: no labeled anomaly data required
  - 100 isolation trees (n_estimators=100)
  - contamination=0.10: top 10% anomalous samples define decision boundary
  - predict() returns +1 (normal) or -1 (anomaly)
  - Path length in random trees is shorter for anomalies (easier to isolate)

INFERENCE FLOW (/api/v1/scan/invoice):
  Input  -> multipart file upload (PDF, PNG, JPG, TXT)
  Step 1 -> process_invoice_file() -> OCR -> feature dict
  Step 2 -> pd.DataFrame([features_dict])
  Step 3 -> registry.invoice_model.predict(df)[0] -> +1 or -1
  Step 4 -> verdict = "SUSPICIOUS" if pred==-1 else "CLEAN"
  Step 5 -> explanations generated from feature thresholds
  Output -> { extractedFields, riskScore, verdict, flaggedExplanations }

4.3 Compliance Document NLP Classifier
----------------------------------------
File    : backend/ml/train_compliance.py
Model   : Pipeline [ TF-IDF Vectorizer + Logistic Regression ]
Artifact: backend/models/compliance_model.joblib (29 KB)

CLASSIFICATION CATEGORIES:
  CLEAN                      - Standard, compliant financial clause
  AML_RED_FLAG               - Anti-Money Laundering violation
                               (offshore transfers, shell companies,
                               smurfing / structuring below threshold)
  SOX_VIOLATION              - Sarbanes-Oxley violation
                               (unauthorized statement edits, disabled audit
                               logs, lack of segregation of duties)
  TAX_EVASION_SUSPICION      - Off-the-books transactions, disguised fees,
                               backdated contracts, unreported income
  UNAUTHORIZED_PAYMENT_TERMS - Overridden payment terms, unsigned contracts,
                               duplicate payments, post-signature alterations

TEXT VECTORIZATION - TF-IDF:
  TfidfVectorizer(ngram_range=(1, 2), max_features=5000)
  - Converts text clauses into a sparse TF-IDF feature matrix
  - Unigrams + Bigrams: captures contextual phrases like "offshore account",
    "audit logs disabled", "net 90 terms overridden"
  - IDF weighting: down-weights common words, emphasizes rare indicator terms
  - max_features=5000: keeps the feature space manageable

ALGORITHM - Logistic Regression:
  - class_weight='balanced': compensates for class imbalance
  - max_iter=1000: ensures convergence on high-dimensional TF-IDF space
  - Multi-class via one-vs-rest (OvR) strategy
  - predict_proba() provides per-class confidence scores

TRAINING DATA:
  5,000 synthetic labeled samples across 5 categories (1,000 each).
  Templates per category:
  - CLEAN: 7 templates (standard invoices, travel expenses, salary deposits)
  - AML_RED_FLAG: 5 templates (offshore transfers, shell companies, smurfing)
  - SOX_VIOLATION: 5 templates (unauthorized edits, disabled audit logs)
  - TAX_EVASION_SUSPICION: 5 templates (cash payments, backdated contracts)
  - UNAUTHORIZED_PAYMENT_TERMS: 5 templates (overridden terms, duplicates)
  Random year annotations added to 50% of samples for lexical diversity.

INFERENCE FLOW (/api/v1/scan/compliance):
  Input  -> JSON { "text": "..." } OR multipart PDF/TXT file
  Step 1 -> Parse content-type header to branch JSON vs multipart handling
  Step 2 -> PDF: pdfplumber inline extraction; TXT: raw decode
  Step 3 -> Split into clauses: re.split(r'\n|\.', text)
             Filter clauses with len > 10 characters
  Step 4 -> registry.compliance_model.predict(clauses) -> class labels
            registry.compliance_model.predict_proba(clauses) -> scores
  Step 5 -> Collect non-CLEAN clauses with confidence and riskTag
            overall_risk = max confidence across all flagged clauses
  Output -> { documentRiskScore, verdict, flaggedClauses[] }

      tax_to_subtotal_ratio: float
      line_item_sum_delta: float
      round_amount_score: int
      amount_z_score: float
    riskScore: float          (10.0 for CLEAN, 90.0 for SUSPICIOUS)
    verdict: str              ("CLEAN" or "SUSPICIOUS")
    flaggedExplanations: List[str]

  ComplianceResponse (untyped dict):
    documentRiskScore: float  (max confidence of flagged clauses, or 5.0)
    verdict: str              ("CLEAN" or "FLAGGED")
    flaggedClauses: List[dict]
      clause: str
      riskTag: str            (AML_RED_FLAG | SOX_VIOLATION | etc.)

8.2 Key Learnings
------------------

  1. END-TO-END ML SYSTEM DESIGN
     Building a complete ML platform requires skills far beyond model training:
     feature engineering, serialization, API contract design, and fallback
     strategies are equally important as model accuracy.

  2. SCIKIT-LEARN PIPELINE PATTERN
     Encapsulating preprocessing + classification inside sklearn Pipeline is
     essential. It serializes the complete transform chain into one .joblib
     file, eliminating training/serving skew - a critical production concern.

  3. UNSUPERVISED ANOMALY DETECTION (ISOLATION FOREST)
     IsolationForest is ideal for invoice fraud because labeled fraud samples
     are scarce. The algorithm leverages the principle that anomalies are
     "few and different" - they are easier to isolate in random partitioning
     trees (shorter path length = higher anomaly score).

  4. NLP FEATURE ENGINEERING WITH TF-IDF
     TF-IDF with bigrams (ngram_range=(1,2)) is surprisingly effective for
     short regulatory clause classification. Bigrams capture key phrases
     like "offshore account", "audit logs", and "shell company" that carry
     strong classification signal.

  5. OCR IN PRODUCTION ENVIRONMENTS
     pdfplumber works well for digitally created PDFs but returns empty text
     for scanned/image-based PDFs. For those, pytesseract (Tesseract engine)
     is required but depends on a system-level Tesseract binary installation.
     Production systems should use cloud OCR (Google Document AI, AWS Textract)
     for higher accuracy and reliability.

  6. FIREBASE CORS AND CLOUD CONFIGURATION
     Firebase Storage requires explicit CORS policy via gsutil - this cannot
     be configured through the Firebase Console UI alone. The disconnect
     between Firebase Console features and Google Cloud Console features is
     a common source of confusion in production deployments.

  7. REAL-TIME STATE WITH FIRESTORE LISTENERS
     Firebase onSnapshot creates a persistent connection enabling true
     real-time UI updates. Combining this with a custom local event bus
     (JavaScript Set of callbacks) provides consistent behavior whether
     Firestore is available or not.

  8. AXIOS INTERCEPTORS FOR ML BACKEND RESILIENCE
     ML backends often experience cold starts (model loading delays) that
     cause initial 503 errors. An automatic retry interceptor with a 2-second
     delay transparently handles this, significantly improving perceived
     reliability without any UI changes.

  9. GRACEFUL DEGRADATION ARCHITECTURE
     Every integration point (Firebase Storage, Firestore, ML backend) has
     a documented fallback. This "graceful degradation" pattern ensures the
     application remains functional in partial failure scenarios, which is
     especially important during development and deployment transitions.

 10. PYDANTIC FOR API CONTRACTS
     FastAPI's tight integration with Pydantic enforces request/response
     schemas at runtime, provides automatic input validation, and generates
     OpenAPI documentation without additional effort.

8.3 Challenges Overcome
------------------------

  Challenge 1: Firebase Storage CORS Block
    Problem : Firebase Storage blocked all upload requests from localhost:5173.
              The error "Response to preflight request doesn't pass access
              control check" is a server-side rejection of browser CORS preflight.
    Solution: Bypassed the network request entirely using URL.createObjectURL()
              as the storage URL. The cloud upload code is preserved in comments
              in storageService.js. A cors.json file was prepared for future
              deployment via gsutil cors set command.

  Challenge 2: joblib Deserialization of Custom Sklearn Transformer
    Problem : Loading phishing_model.joblib failed with "Cannot find class
              URLFeatureExtractor" because it was defined in a training script,
              not an importable Python module.
    Solution: model_loader.py dynamically adds the ml/ directory to sys.path
              and injects URLFeatureExtractor into __main__.__dict__ before
              calling joblib.load(), satisfying Python's pickle deserialization
              class lookup mechanism.

  Challenge 3: Dual Content-Type Compliance Endpoint
    Problem : The compliance scanner needed to accept both plain text (JSON)
              from a textarea and file uploads (multipart/form-data) from
              a file input - two completely different HTTP content types.
    Solution: Inspected request.headers["content-type"] at runtime to branch
              the parsing logic within a single FastAPI endpoint handler.

  Challenge 4: Firestore Composite Index Requirement
    Problem : Combined where() + orderBy() Firestore queries require pre-built
              composite indexes in Firebase Console or they return index errors.
    Solution: The localStorage fallback transparently provides equivalent data
              when Firestore queries fail. Index creation links are provided in
              Firestore error messages for when this is needed in production.

  Challenge 5: Invoice Model Feature Alignment
    Problem : Feature names in the training DataFrame must exactly match those
              used during inference. A single key mismatch causes a silent
              prediction failure or ValueError.
    Solution: Both ocr_service.py and train_invoice.py use the same explicit
              feature dict keys: tax_to_subtotal_ratio, line_item_sum_delta,
              round_amount_score, amount_z_score.
